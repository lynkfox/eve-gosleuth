# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An EVE Online intel tool written in Go (module `github.com/lynkfox/go_eve_sleuth`). It pulls a target's killmails from zKillboard, fills in the details from CCP's ESI API, and aggregates them into stats such as most frequent fleetmates, systems, ships, battles, and capital pilots. `Readme.md` is the feature to-do list for pilot, corp/alliance, and system intel.

## Commands

```bash
wails build -platform windows/amd64 -skipbindings   # GUI -> build/bin/eve-gosleuth.exe (wails CLI v2: go install github.com/wailsapp/wails/v2/cmd/wails@v2.17.0)
go run ./cmd/cli                        # CLI scratch driver (target is hardcoded in cmd/cli/main.go)
go test ./...                           # all tests
go test ./aggregate -run TestName -v    # single test
GOOS=windows go vet ./...               # vet including the Wails windows code
```

- The GUI is a Wails v2 app targeting **Windows**, developed in WSL. WSL has no GTK/WebKit, so `wails dev` and Linux GUI builds don't work there; cross-build the Windows exe from WSL (Wails on Windows needs no cgo) and run it from Windows. `-skipbindings` is required, since generating bindings builds and runs a Linux binary.
- A plain `go build` of the root package without Wails build tags produces a binary that refuses to run; always build the GUI with `wails build`.
- The cache lives at `retrieval.DefaultCachePath()`: `%LocalAppData%\eve-gosleuth\cache.db` (SQLite) on Windows, `~/.cache/eve-gosleuth/` on Linux, unless the user moved it in Preferences (`Settings.CacheDir`). An old `cached_data.json` beside it has its killmails imported once and is then removed.

## GUI

- `main.go` runs Wails, embedding `frontend/dist`. The GUI backend is package `gui`: `App` (gui/app.go) is bound to the frontend, and each exported method is callable from JS as `window.go.gui.App.<Method>()` and returns a Promise. `startup` loads static data, clients, and the cache; `shutdown` saves and closes the cache. They are unexported and handed to Wails by `gui.Lifecycle`, since Wails offers every exported method to the frontend. The Members tab is gui/members.go, Preferences and themes gui/settings.go, and the cache actions gui/cache.go.
- Wails calls bound methods concurrently, so every `App` method takes `a.mu` (the cache maps are not thread safe) and uses `defer recoverAsError(&err)` so a panic becomes a frontend error instead of crashing the window.
- `frontend/dist` is hand-written HTML/CSS/JS, **not build output**: there is no Node/Vite step (`frontend:install`/`frontend:build` are empty in wails.json). Wails injects its runtime scripts into `index.html` automatically. Set text via `textContent`, never `innerHTML`, since names come from ESI.
- `api/esi_gui.go` builds `TargetDisplay` values (four title/value panels) per entity type via `TargetEntity.BuildDisplay`; many values are still placeholders. `api.EntityImageURL` gives EVE image server portraits/logos.
- `build/appicon.png` and `build/windows/` (icon, manifest, info.json) were generated by `wails build` and are committed; `build/bin/` is ignored.

## Pipeline / architecture

Data moves through the packages in this order (see `cmd/cli/main.go` or `App.CollectIntel`):

1. **`comm`**: global state that must be set up first. `comm.InitLogger(level)` sets the package-level `comm.Logger` (logrus, JSON to stdout). Code everywhere calls `comm.Logger` directly, so tests must init it too. `comm.InitStaticData(staticdata.Files)` loads the JSON ID→name maps into the globals `CapitalShips`, `ControlTowers`, and `UpwellStructures`; the JSON files are embedded into the binary by the `static_data` package (imported as `staticdata`). A copy of any of them in a `static_data` folder beside the exe (`staticdata.Overrides()`) is used instead, so game data can change without a rebuild; a missing or unreadable copy falls back to the embedded one. Game data such as type and group ids belongs in these files, not in Go constants. `space_classes.json` holds the wormhole region letter classes and regions with their own kind of space (Pochven is Triglavian), loaded into `comm.Spaces`. Rules for how codes are read, such as the NPC corp id range and the security bands (`api.SecurityBand`, which the frontend gets as `securityBand` rather than working out itself), stay in code. `comm.LogFields` helpers add fields only at Debug level.
2. **`api`**: HTTP clients. `APIConnection` (generic.go) implements `APIClient` with retries and exponential backoff. `ZkillConnection` and `ESIConnection` wrap an `APIClient` and are exposed through the `ZkillClient` / `ESIClient` interfaces. Tests replace the `APIClient` with `MockApiClient` (api/generic_test.go). zKill responses are gzip-decoded.
3. **`retrieval`**: turns raw API data into readable models.
   - `IntelTarget` (target.go) is the subject being investigated. It holds an ID, an `EntityType` (`comm/types`), a `CollectionClientPool` with both clients, and `Expanded` (the readable `*Pilot`/`*Corporation`). `aggregate` type-asserts `Expanded` based on `TypeOfEntity`.
   - `CollectKillmails` fetches the zKill list (newest first, up to 10 pages of 200), then the ESI killmail for each one, producing `[]RawKillmail{Zkillmail, ESIKillmail}`. `KillmailLimits` decides how many: a max count (default `DefaultKillmailLimit`, 20, or `AllKillmails` (-1) for every killmail zKill lists), an optional cutoff date, and whether to also use cached killmails beyond those limits. The GUI takes these from the Preferences window (`gui/settings.go`); the CLI uses `DefaultKillmailLimits()`. Progress for long steps is reported with `comm.ReportProgress`, which the GUI shows in its ticker.
   - `CachedEveIDs` (caching.go) caches **every** ESI response and is itself an `api.ESIClient` (cached_esi.go): the app passes the cache, never the raw client, as `Clients.ESIClient`, and the cache fetches misses with its own uncached `Client`. `Known` holds raw ESI responses and `Expanded` readable models, both keyed by eve ID as `CacheEntry{Value, CachedAt, Permanent}`; `Killmails`, `NameLookups` (universe/ids), and `EntityNames` (universe/names) are separate maps because their keys can clash with eve IDs. Expiry: pilots, corporations, and alliances (raw or expanded) are refetched after 24 hours (`volatileTTL`, decided at read time by `ttlFor[T]` from `CachedAt`); killmails are `Permanent` and never expire; everything else expires only when a newer SDE is released. The app reads `releaseDate` from developers.eveonline.com/static-data/tranquility/latest.jsonl (`api.SDEClient`, at startup and at most hourly before searches) and `UpdateSDERelease` drops everything cached before it, killmails excepted. Read with `GetIfNotCached` or `FetchExpanded[T]`; write with `Update`/`UpdateExpanded`, which always overwrite. A mutex makes the cache safe for concurrent use. The maps only hold what the session has used: a miss in `cachedAs` reads the row from the SQLite database (store.go, pure Go `modernc.org/sqlite`, one `cache` table keyed by `section` and key, killmails gzipped), and every write goes through `put`, which marks it dirty for `SaveCache` to write in one transaction. Always pass the map's matching `section` to `cachedAs`/`put`. A cached value whose own eve id is 0 (`missingID`) is fetched again once on access and the fixed copy cached; if that refetch fails the cached copy is returned and the next lookup tries again. Bump `schemaVersion` (store.go) when the table layout changes; a database with another version is emptied.
   - `LoadCache` always returns a usable cache (a missing, empty, or old-version file starts empty; a corrupt file is renamed to `.corrupt`). `SaveCache` writes a temp file and renames it into place. A cached value whose own eve id is 0 (`missingID`) is fetched again once on access and the fixed copy cached; if that refetch fails the cached copy is returned and the next lookup tries again. Bump `schemaVersion` (store.go) when the table layout changes; a database with another version is emptied.
   - `RawKillmail.Expand` and `cached.ExpandPilot/Corporation/Alliance/System/Item` build the readable `Killmail` model (killmail_models.go), filling nested corp/alliance data through the cache.
4. **`aggregate`**: `CollateAllKillmailData` walks the killmails in order and fills `CollectedData` (collated_models.go): maps of `PilotSeen`, `SystemVisted`, `ShipFlown`, `BattleFought`, `CapitalPilot`, `AllianceSeen`, and `CorporationSeen`. Consecutive killmails within 15 minutes in the same system are grouped into one battle. Query functions like `GetMostFrequentFleetmates` (pilotsSeen.go) read from `CollectedData`. `GetPIPilots` (piPilots.go) feeds a system target's PI Pilots tab: hauler losses, T1 and T2 transports but no freighters (`hauler_groups.json` minus `hauler_exclusions.json`) whose zKill `locationID` (`Killmail.LocationID`, the nearest celestial) is one of the system's planets, plus any loss with PI aboard wherever it died (the victims' item types are prefetched with `PrefetchItemTypes` first), with PI cargo found by item group (`pi_material_groups.json`) from the raw `Victim.Items`. `GetRatters` (ratters.go) feeds its Ratters tab: any pilot loss with an NPC attacker (no character, in an NPC corp or none, so structures are not rats), each tagged by who else was on it: NPCs only, players using only smartbombs (weapon group in `smartbomb_groups.json`), or other players; pilots with the surest loss rank first.

## Conventions

- Doc comments on exported functions use a `/* Name ... Parameters: ... Returns: ... */` block style.
- Errors are sentinel values on small custom types (`RequestError`, `TargetError`) wrapped with `fmt.Errorf("%w ...")`. Many call sites still have `//handle error` placeholders.
- Tests live in external `_test` packages (e.g. `package api_test`) and use testify `assert`. The exceptions are `settings_test.go` and `app_test.go`, which are `package main` because main can not be imported.
- User settings (the Settings > Themes choice, Preferences, and the order the intel tabs were dragged into, `Settings.TabOrder` via `SetTabOrder`) are saved by `gui/settings.go` to `settings.json` beside the cache. The tab order in `index.html` is the default; a saved order fills the slots of the tabs it names (`tabOrderFrom` in main.js), so a new tab keeps its default place.
- The search bar's recent searches live in the cache, not settings (retrieval/recent_searches.go): `SearchTarget` calls `AddRecentSearch` with each found target as EVE spells it, one `Permanent` row per search in the `recent_search` section keyed by type and lower case name, keeping the number set in Preferences (`Preferences.MaxRecentSearches`, default `DefaultRecentSearches` 5, at most `MaxRecentSearches` 25; lowering it calls `TrimRecentSearches`); the × on a row calls `RemoveRecentSearch`. An SDE release keeps them; Clear everything and Clear older than remove them. Themes themselves are defined in `frontend/dist/main.js` (`THEMES`); only colors without a meaning are themed, kill/loss, security, and wormhole class colors stay fixed.
