# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An EVE Online intel tool written in Go (module `github.com/lynkfox/go_eve_sleuth`). It pulls a target's killmails from zKillboard, fills in the details from CCP's ESI API, and aggregates them into stats such as most frequent fleetmates, systems, ships, battles, and capital pilots. `Readme.md` is the feature to-do list for pilot, corp/alliance, and system intel.

## Commands

```bash
wails build -platform windows/amd64 -skipbindings   # GUI -> build/bin/eve-gosleuth.exe (wails CLI v2: go install github.com/wailsapp/wails/v2/cmd/wails@v2.17.0)
go run ./cmd/cli                        # CLI scratch driver (target is hardcoded in cmd/cli/main.go)
go test ./...                           # all tests
go test ./aggregate -run TestName -v    # single test
GOOS=windows go vet ./...               # vet including the Wails windows code
```

- The GUI is a Wails v2 app targeting **Windows**, developed in WSL. WSL has no GTK/WebKit, so `wails dev` and Linux GUI builds don't work there; cross-build the Windows exe from WSL (Wails on Windows needs no cgo) and run it from Windows. `-skipbindings` is required, since generating bindings builds and runs a Linux binary.
- A plain `go build` of the root package without Wails build tags produces a binary that refuses to run; always build the GUI with `wails build`.
- The cache lives at `retrieval.DefaultCachePath()`: `%LocalAppData%\eve-gosleuth\cache.db` (SQLite) on Windows, `~/.cache/eve-gosleuth/` on Linux, unless the user moved it in Preferences (`Settings.CacheDir`). An old `cached_data.json` beside it has its killmails imported once and is then removed.

## GUI

- `main.go` runs Wails, embedding `frontend/dist`. The GUI backend is package `gui`: `App` (gui/app.go) is bound to the frontend, and each exported method is callable from JS as `window.go.gui.App.<Method>()` and returns a Promise. `startup` loads static data, clients, and the cache; `shutdown` saves and closes the cache. They are unexported and handed to Wails by `gui.Lifecycle`, since Wails offers every exported method to the frontend. The Members tab is gui/members.go, Preferences and themes gui/settings.go, and the cache actions gui/cache.go.
- Wails calls bound methods concurrently, so every `App` method takes `a.mu` (the cache maps are not thread safe) and uses `defer recoverAsError(&err)` so a panic becomes a frontend error instead of crashing the window. Methods that only touch the cache (`GetRecentSearches`, `GetHoldings`, `SaveHolding`, `RemoveHolding`) skip `a.mu`, since the cache has its own lock and they must not wait behind a search. The other exceptions are `AnswerPrompt` and `StopSearch` (gui/search_control.go), which must reach a search that holds `a.mu`: a search asks the frontend a question with `ask` (a Wails event) and waits for `AnswerPrompt`. `StopSearch` halts the ESI `RateGuard` (`api.ErrStopped` for every request), so killmail collection ends where it is and the report is built from what is cached; `SearchTarget` and `CollectIntel` resume it when they return, and the report's `stopped`/`rateLimited` flags show a warning above it.
- `frontend/dist` is hand-written HTML/CSS/JS, **not build output**: there is no Node/Vite step (`frontend:install`/`frontend:build` are empty in wails.json). Wails injects its runtime scripts into `index.html` automatically. Set text via `textContent`, never `innerHTML`, since names come from ESI.
- The search bar has no type: `SearchTarget(name, "")` looks the name up with `retrieval.MatchTargets` (ESI universe/ids: exact names ignoring case, plus corps and alliances by ticker, ie Jita Holding Inc. (JITA) for Jita, kept as `ByTicker` since a player may only have seen a ticker; items left out) and searches a lone exact match, or with more than one or any by ticker returns `TargetResult.Choices`, ticker ones last, for `chooseTarget` (main.js, `#target-choice`) to ask which, then is called again with the chosen name and type. A typed lookup (`GetTargetInfoOfType`) prefers the exact name among its type. A name filled in by the app, ie a recent search or a menu's Search, carries its type as `searchTypeHint`, cleared by typing.
- The window itself never scrolls (end of style.css): the header, target panel, and tab bar stay put and each `.tab-panel` scrolls on its own. A paged tab (`.paged-panel`, Killmails and Members) scrolls only its `.panel-scroll` list, keeping its pager in reach. The search limits button beside the search bar (`#limits-button`, gui/search_limits.go) changes what searches collect (max, pages, newer than, cached, holdings) until the app closes: `SetSearchLimits` keeps them on `App.searchLimits` (under `settingsMu`, so it skips `a.mu`), `searchPreferences()` is the Preferences with them in place and is what `CollectIntel` and `holdingMain` read, and `SaveSearchLimits` makes them the defaults; the button is in the accent while it has its own. The Collapse target on search preference (`Preferences.CollapseTarget`) pulls the target panel shut at each search. As the app launches, `showCaveatWarning()` opens the killmail caveat warning (`#caveat-warning`) while `Preferences.ShowCaveatWarning` (on by default) is on; its Don't show this again box calls `DismissCaveatWarning`.
- `api/esi_gui.go` builds `TargetDisplay` values (four title/value panels) per entity type via `TargetEntity.BuildDisplay`; many values are still placeholders. `api.EntityImageURL` gives EVE image server portraits/logos.
- `build/appicon.png` and `build/windows/` (icon, manifest, info.json) were generated by `wails build` and are committed; `build/bin/` is ignored.

## Pipeline / architecture

Data moves through the packages in this order (see `cmd/cli/main.go` or `App.CollectIntel`):

1. **`comm`**: global state that must be set up first. `comm.InitLogger(level)` sets the package-level `comm.Logger` (logrus, JSON to stdout). Code everywhere calls `comm.Logger` directly, so tests must init it too. `comm.InitStaticData(staticdata.Files)` loads the JSON ID→name maps into the globals `CapitalShips`, `ControlTowers`, and `UpwellStructures`; the JSON files are embedded into the binary by the `static_data` package (imported as `staticdata`). A copy of any of them in a `static_data` folder beside the exe (`staticdata.Overrides()`) is used instead, so game data can change without a rebuild; a missing or unreadable copy falls back to the embedded one. Game data such as type and group ids belongs in these files, not in Go constants. `space_classes.json` holds the wormhole region letter classes and regions with their own kind of space (Pochven is Triglavian), loaded into `comm.Spaces`. Rules for how codes are read, such as the NPC corp id range and the security bands (`api.SecurityBand`, which the frontend gets as `securityBand` rather than working out itself), stay in code. `comm.LogFields` helpers add fields only at Debug level.
2. **`api`**: HTTP clients. `APIConnection` (generic.go) implements `APIClient` with retries and exponential backoff. `ZkillConnection` and `ESIConnection` wrap an `APIClient` and are exposed through the `ZkillClient` / `ESIClient` interfaces. Tests replace the `APIClient` with `MockApiClient` (api/generic_test.go). zKill responses are gzip-decoded.
3. **`retrieval`**: turns raw API data into readable models.
   - `IntelTarget` (target.go) is the subject being investigated. It holds an ID, an `EntityType` (`comm/types`), a `CollectionClientPool` with both clients, and `Expanded` (the readable `*Pilot`/`*Corporation`). `aggregate` type-asserts `Expanded` based on `TypeOfEntity`.
   - `CollectKillmails` fetches the zKill list (newest first, pages of 200 up to zKill's 100; a page short of 200 ends it, except a nearly full page 1 (`zkillNearlyFullPage`), since zKill holds back the newest killmails, under five minutes old, and the page after it failing is then the end of the list; a killmail listed twice is kept once). zKill sends the whole ESI killmail with each entry (`ZkbResponse.Killmail()`), so each killmail is the cache's copy, else zKill's (then cached with `StoreKillmail`), else fetched from the ESI; the ESI is only asked for an entry missing its time, system, victim's ship, or attackers, at most `MaxESIKillmails` (1700) a search, the rest skipped with `ErrTooManyESIKillmails`. Only the entries within Max are looked up in the cache, all of them with `IncludeCached`. Paging also stops at the page reaching `NewerThan`; when even the newest killmail is older, `ConfirmIgnoreDate` is asked up front and a yes lists again further back. Each entity's list is cached (retrieval/zkill_lists.go, section `zkill_list`, gzipped, `Permanent`): `KnownZkillList` keeps zKill's data for each killmail and how many from the top are `Unbroken` (no gap), and every killmail zKill sends, past the limits too, is cached with `StoreKillmail` as it is listed. `listEntity` stops paging at the first page reaching the cached list's unbroken part (`ZkillPaging.Known`) and splices the rest in; when the search needs more than is unbroken it carries on from there (`ZkillPaging.StartPage`). Entries past the limits that only the cached list has are used only with `IncludeCached`. Late-posted old killmails deep in a list are not picked up by a search that stops early. This produces `[]RawKillmail{Zkillmail, ESIKillmail}`, and the names, pilots, corps, and the rest the killmails refer to are looked up in bulk afterwards (`PrefetchKillmailEntities`). `KillmailLimits` decides how many: a max count (default `DefaultKillmailLimit`, 20, up to 20,000; zKill is paged only until that many are listed), or `AllKillmails` (-1) for every killmail on the first `Pages` pages (default `DefaultKillmailPages`, 10), an optional cutoff date, and whether to also use cached killmails beyond those limits. The GUI takes these from the Preferences window (`gui/settings.go`); the CLI uses `DefaultKillmailLimits()`. When even the newest killmail is older than `NewerThan`, `ConfirmIgnoreDate` decides whether to drop the date limit for that search. A 429 from the ESI returns `api.ErrRateLimited`: the `RateGuard` (api/ratelimit.go) does not retry it, holds that rate limit group for at least 15 minutes (`ESI_RATE_LIMIT_HOLD`) so its requests fail at once, and calls `comm.ReportRateLimited`, which the GUI shows as a popup. Killmails that needed the ESI are then skipped, the rest are still used, and `CollectIntel` builds the report with a warning above it. Progress for long steps is reported with `comm.ReportProgress`, which the GUI shows in its ticker.
   - `CachedEveIDs` (caching.go) caches **every** ESI response and is itself an `api.ESIClient` (cached_esi.go): the app passes the cache, never the raw client, as `Clients.ESIClient`, and the cache fetches misses with its own uncached `Client`. `Known` holds raw ESI responses and `Expanded` readable models, both keyed by eve ID as `CacheEntry{Value, CachedAt, Permanent}`; `Killmails`, `NameLookups` (universe/ids), and `EntityNames` (universe/names) are separate maps because their keys can clash with eve IDs. Expiry: pilots, corporations, and alliances (raw or expanded) are refetched after 24 hours (`volatileTTL`, decided at read time by `ttlFor[T]` from `CachedAt`); killmails are `Permanent` and never expire; everything else expires only when a newer SDE is released. The app reads `releaseDate` from developers.eveonline.com/static-data/tranquility/latest.jsonl (`api.SDEClient`, at startup and at most hourly before searches) and `UpdateSDERelease` drops everything cached before it, killmails excepted. Read with `GetIfNotCached` or `FetchExpanded[T]`; write with `Update`/`UpdateExpanded`, which always overwrite. A mutex makes the cache safe for concurrent use. The maps only hold what the session has used: a miss in `cachedAs` reads the row from the SQLite database (store.go, pure Go `modernc.org/sqlite`, one `cache` table keyed by `section` and key, killmails gzipped), and every write goes through `put`, which marks it dirty for `SaveCache` to write in one transaction. Always pass the map's matching `section` to `cachedAs`/`put`. A cached value whose own eve id is 0 (`missingID`) is fetched again once on access and the fixed copy cached; if that refetch fails the cached copy is returned and the next lookup tries again. Bump `schemaVersion` (store.go) when the table layout changes; a database with another version is emptied.
   - `LoadCache` always returns a usable cache (a missing, empty, or old-version file starts empty; a corrupt file is renamed to `.corrupt`). `SaveCache` writes a temp file and renames it into place. A cached value whose own eve id is 0 (`missingID`) is fetched again once on access and the fixed copy cached; if that refetch fails the cached copy is returned and the next lookup tries again. Bump `schemaVersion` (store.go) when the table layout changes; a database with another version is emptied.
   - `RawKillmail.Expand` and `cached.ExpandPilot/Corporation/Alliance/System/Item` build the readable `Killmail` model (killmail_models.go), filling nested corp/alliance data through the cache.
4. **`aggregate`**: `CollateAllKillmailData` walks the killmails in order and fills `CollectedData` (collated_models.go): maps of `PilotSeen`, `SystemVisted`, `ShipFlown`, `BattleFought`, `CapitalPilot`, `AllianceSeen`, and `CorporationSeen`. Consecutive killmails within 15 minutes in the same system are grouped into one battle. Query functions like `GetMostFrequentFleetmates` (pilotsSeen.go) read from `CollectedData`. `GetTopAllies` (allies.go) feeds the Allies tab of pilot, corp, and alliance targets: the alliances, then corps in no alliance, on the target's kills (not its losses) outside the alliance it was in at each kill, each noting how many of the target's kills its own pilots were the victim of. The user can ignore allies per target from a row's right click menu (every row's menu is built by `withMenu` in main.js from sections, `openSectionsMenu`: a heading per entity on the row, ie the pilot, their corp, and alliance, each with Search and site links, so rows send corps and alliances as `EntityRef`s; an Allies row's section has its own items, Add to Holding and Ignore, above them, and Open shared killmails on zKillboard, `AllySummary.TogetherURL` (`api.ZkillTogetherURL`, one zKill advanced search: the target and every holding searched in Attackers as or, the ally in Either, so its kills with them and their kills of it); a killmail card's menu has only the part right-clicked, `killmailCardSections`: the victim, the final blow, or else the system; saved at once by gui/allies.go `SaveIgnoredAllies`; the × on an ignored one under the table brings it back), saved in the cache's `ignored_ally` section (retrieval/ignored_allies.go) like recent searches; `GetTopAllies` skips them so the next ones take their places, and with the Hide killed allies preference (`Preferences.HideKilledAllies`) every ally the target also killed; `RankAllies` re-ranks the shown search after that preference changes; while it is on and the target killed any (`AllyRanking.KilledAllies`), a toggle tag in the theme's accent leads the left-out tags under the table and re-ranks with `showKilled` to show or hide them for that search only (kept on `alliesSource` until the next search). The ignored tags show the kills each shared (`AllyRanking.IgnoredKillmails`), most first. Holding links (retrieval/holdings.go, section `holding`, gui/holdings.go) tie a corp or alliance to holding corps or alliances by hand; the target panel shows them from both ends (`TargetResult.Holdings`), and Allies leaves out holdings linked to the target's own groups. With the Include holdings preference (`Preferences.IncludeHoldings`, on by default) a corp or alliance search sets `IntelTarget.Holdings` to its own holdings (one level, not the mains it holds for): `CollectKillmails` (`listKillmails`) pulls each holding's zKill list with the same paging and merges them newest first, a killmail on two lists kept once as the main's, before Max and the date limit apply. `RawKillmail.Via`/`Killmail.Via` name the holding a killmail came from, shown as a "via" tag on its card. Searching a holding, while that preference is on, searches its main instead (`holdingMain` in gui/app.go, the first main by name; `TargetResult.SearchedHolding` names the holding for the status line). The Allies tab of a corp or alliance opens with a line of its holdings and the kills each shared with it (`aggregate.HoldingKillsTogether`: kills with pilots of both the main itself and the holding). Holdings count as the target everywhere through `IntelTarget.IsGroup(corpID, allianceID)`: losses, members, capital pilots, and allies; the Members tab's roster stays the main corp's. A killmail whose victim and every attacker are the target or its holdings (`aggregate.IsInternal`, any outside attacker or NPC makes it a normal loss) has the outcome `internal`: still a loss, never a kill, skipped by Allies. Ignored allies and holding links are the user's own data (`userSections`): `ClearAll` and `ClearOlderThan` keep them unless the Clear cache popup's "Also clear what you set by hand" box is checked. Structures (retrieval/structures.go, aggregate/structures.go, gui/structures.go) are pulled with the killmails in `CollectIntel`, before the report, and prefetched with them. A zKill list can be narrowed with `ZkillPaging.Filter` (modifiers put before the entity, ie `losses/groupID/1657`; an entity with a `groupID` means that entity's own ship or structure is in the group), cached apart by `zkillListKey` with the filter. Structure groups are `structure_groups.json` (citadels, engineering complexes, refineries, control towers) and control tower batteries `pos_battery_groups.json`, since a tower is never a killmail attacker, only its batteries. Structures with no guns, Metenox moon drills and customs offices, are `minor_structure_groups.json` and `minor_structures.json`: never a last structure lost, never on kills, but listed among previous losses and Destroyed. A j-space system target gets `IntelReport.LastStructureLoss` and `PreviousStructureLosses` (`retrieval.StructureLosses`, page 1 of each structure and minor structure group's losses in the system, no limits: the newest non-minor loss, and the `PreviousStructureLosses` (5) newest others), the box above its Activity with the others collapsed under it. A corp or alliance target gets the Structures tab (`IntelReport.Structures`): Used in Kills is `CollectStructureKillmails`, each structure group's kills (not towers) and losses, and each battery group's kills, for the target and its holdings, to Max or Pages but ignoring the date limit, then `aggregate.StructuresUsed` groups them by type (towers as one kind), system, and owner corp, as killmails give no structure name or id, grayed by a loss of the same after its newest kill (which also names a tower seen only through batteries). Destroyed is `aggregate.StructuresDestroyed`, the structure and minor structure losses on the search's own killmails that the target's pilots were on. `GetPIPilots` (piPilots.go) feeds a system target's PI Pilots tab: hauler losses, T1 and T2 transports but no freighters (`hauler_groups.json` minus `hauler_exclusions.json`) whose zKill `locationID` (`Killmail.LocationID`, the nearest celestial) is one of the system's planets, plus any loss with PI aboard wherever it died (the victims' item types are prefetched with `PrefetchItemTypes` first), with PI cargo found by item group (`pi_material_groups.json`) from the raw `Victim.Items`. `GetRatters` (ratters.go) feeds its Ratters tab: any pilot loss with an NPC attacker (no character, in an NPC corp or none, so structures are not rats), each tagged by who else was on it: NPCs only, players using only smartbombs (weapon group in `smartbomb_groups.json`), or other players; pilots with the surest loss rank first.

## Conventions

- Doc comments on exported functions use a `/* Name ... Parameters: ... Returns: ... */` block style.
- Errors are sentinel values on small custom types (`RequestError`, `TargetError`) wrapped with `fmt.Errorf("%w ...")`. Many call sites still have `//handle error` placeholders.
- Tests live in external `_test` packages (e.g. `package api_test`) and use testify `assert`. The exceptions are `settings_test.go` and `app_test.go`, which are `package main` because main can not be imported.
- User settings (the Settings > Themes choice, Preferences, and the order the intel tabs were dragged into, `Settings.TabOrder` via `SetTabOrder`) are saved by `gui/settings.go` to `settings.json` beside the cache. The tab order in `index.html` is the default; a saved order fills the slots of the tabs it names (`tabOrderFrom` in main.js), so a new tab keeps its default place.
- The search bar's recent searches live in the cache, not settings (retrieval/recent_searches.go): `SearchTarget` calls `AddRecentSearch` with each found target as EVE spells it, with a corp's or alliance's ticker (`TargetDisplay.Ticker`, also on `RelatedEntity`, shown EVE style, [CORP] and <ALLY>, by `formatTicker`; a typed ticker finds its recent search), one `Permanent` row per search in the `recent_search` section keyed by type and lower case name, keeping the number set in Preferences (`Preferences.MaxRecentSearches`, default `DefaultRecentSearches` 5, at most `MaxRecentSearches` 25; lowering it calls `TrimRecentSearches`); the × on a row calls `RemoveRecentSearch`. An SDE release keeps them; Clear everything and Clear older than remove them. Themes themselves are defined in `frontend/dist/main.js` (`THEMES`); only colors without a meaning are themed, kill/loss, security, and wormhole class colors stay fixed.
