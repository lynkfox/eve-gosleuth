# Fits plan

How victim fits are read, shown, exported, tagged, and (later) analysed. The phases are in build order. When a phase lands, its behaviour moves into `docs/features.md` and it is struck from here.

## Where things stand

- `retrieval.FitItem` exists and `aggregate` already collects `ShipFlown.Fits` / `Structure.Fits`, but nothing fills `KillmailVictim.Fit`: `RawKillmail.Expand` copies only the raw `Victim.Items`.
- `api.ESIItem` keeps only the name and group. `/universe/types/{id}` also returns `dogma_attributes` and `dogma_effects`, which we discard. Every phase below needs them.

## Phase 1: read the fit from the victim

**Status (2026-10-27): built.** `cmd/sdegen`, `comm/fit_types.go`, `comm/inventory_flags.go`, `retrieval/fits.go`, and `retrieval/eft.go` are written and tested; the CLI prints the target's losses as EFT, and the Fits tab shows them (each entry carries its EFT, so there is no separate App call). Not yet done: importing several exports in-game, especially to check pyfa's blank line after the header.

1. **Type data comes from a trimmed SDE extract**, `static_data/fit_types.json`, generated by `go run ./cmd/sdegen` (decided 2026-10-27). For each type it holds the name, group, category, module slot, hull slot counts, and T3 subsystem slot modifiers. Regenerate it when a new SDE adds hulls or modules. A type newer than the extract falls back to the ESI for its name and is placed by its flag alone.
2. **Slot flags go in static data,** as `static_data/inventory_flags.json`. The starting point is the user's flag list from an older project. It gets checked against real killmails and an invFlags dump, since the JSONL SDE no longer ships invFlags. Special holds are named, and they read either as cargo (the ammo hold, the booster bay) or as ignored:

   | Flag | Slot |
   |---|---|
   | 11–18 | Low |
   | 19–26 | Mid |
   | 27–34 | High |
   | 92–99 | Rig |
   | 125–132 | Subsystem |
   | 87 | Drone bay |
   | 158 | Fighter bay |
   | 88 | Booster |
   | 89 | Implant |
   | 5 | Cargo |
   | 164–171 | Structure service |
3. **Module or charge.** A loaded charge has the same flag as its module. The extract gives a module its slot, from the `hiPower` / `medPower` / `loPower` / `rigSlot` / `subSystem` / `serviceSlot` effect. A type with no slot sharing that flag is the module's charge.
4. **Build a `Fit`** in `RawKillmail.Expand`, replacing the flat `[]*FitItem`:
   - It has `Highs`, `Mids`, `Lows`, `Rigs`, `Subsystems`, `Drones` and `Cargo`, plus the hull's slot counts.
   - Merge the destroyed and dropped entries for the same type and flag.
   - Pair each charge with its module.
   - Keep only this cargo: boosters, scripts, nanite paste, charges and ammo. These are group lists in static JSON, extending `ammo_types.json`. Quantities need not be exact.
5. **Slot counts** come from the hull's attributes: `hiSlots`(14), `medSlots`(13), `lowSlots`(12), `rigSlots`(1137) and `serviceSlots`(2056). For a T3 cruiser, add each subsystem's slot modifiers (1374/1375/1376).
6. **Fetch during the search,** never lazily from a tab: only types missing from the extract need the ESI, and they are prefetched before the killmails are expanded.
7. **EFT text first.** `Fit.EFT(title)` is built before any fitting window, and the CLI prints the target's losses as EFT for testing. The fitting window waits until extraction is proven.
8. **Tests:** table-driven, built from real ESI killmail JSON:
   - a T3 cruiser
   - a hull with empty slots
   - a ship with a drone bay
   - a structure
   - one fit whose modules all dropped, and one whose modules were all destroyed

### Decisions from the first real run (2026-10-27)

- **Capsules are not fits.** A capsule loss is left out of the Fits tab, except when the same pilot loses a capsule with implants in the same system and battle, after a ship. Those implants then belong with that ship loss, shown in a way still to be designed.
- **Nested items are ignored entirely.** Ships in a maintenance bay, ships in an escape bay, and container contents are escape ships, cap-stick trucks, or cargo, so they don't matter here. The ESI item struct already drops them.
- **Modules with no slot in the SDE** (built-in hull weapons such as the Lux Kontos, quantum cores, the moon drill) can be ignored. They are still placed by their flag.
- **Tactical destroyer modes** wait for phase 4, where they change live stats.

## Phase 2: Fits tab, fitting window, and EFT export

### Which searches

- Pilot, corporation and alliance searches get a **Fits** tab.
- System searches do not.

### Tab layout

**Left: the fit list**

- A scrolling list of the target's losses with a fit, grouped by hull.
- Each row shows the hull icon and name, the pilot (for corp and alliance searches), the date, and the system.
- A count marks identical fits merged into one row. Two fits are identical when they have the same hull and the same modules in each slot group, whatever the charges or cargo.
- Corp and alliance searches merge identical fits across pilots, grouped under the ship (decided 2026-10-27), and list the pilots who flew each.

**Right: the fitting window**

- One fitting window, rebuilt in place whenever a row in the list is selected. It is a pane of the tab, not a popup.
- The hull render (`images.evetech.net/types/{id}/render`) is in the centre, with slot icons around it:
  - highs on the top arc, mids on the right, lows on the bottom
  - rigs and subsystems on the inner left
  - an empty slot is drawn as a hollow socket
  - a loaded charge is a small badge on its module
- Drones, fighters, and the kept cargo are listed below or beside the ring.
- The ring is positioned with CSS trig, so no new libraries. Names are set with `textContent`.
- An **Export EFT** button sits in the window's header (see EFT export).
- Leave room in the window for the phase 4 numbers (resists, EHP, repair, ewar). Where they show is still undecided.

### Getting to a fit from elsewhere

- Killmails get **no popup**.
- The killmail row's right-click menu gains **"Show fit"**. It switches to the Fits tab, selects that killmail's fit in the list, scrolls it into view, and rebuilds the fitting window.
- The item appears only when the victim is the target or one of its holdings and the loss has a fit.
- Per the right-click menu rule, the item gets no help text of its own.

### EFT export

- The button copies the fit to the clipboard through the Wails runtime.
- The text is built in Go (an `App` method), so it can be unit-tested. In order:
  1. Header `[Hull, GoSleuth - Pilot - KM#]`.
  2. Lows, then mids, highs, rigs and subsystems, with a blank line between groups.
  3. `Module, Charge` for a loaded module, and `[Empty Low slot]` (and so on) for an empty slot.
  4. Drones as `Name xN`.
  5. Cargo as `Name xN`. Boosters go here too, since the in-game importer is fussier about a separate booster section.
- Check several exports by importing them in-game before calling this done.

## Phase 3: tags

**Rules come first.** The rules live in `static_data/fit_tag_rules.json`, so they can be tuned next to the exe without a rebuild.

- Each module group or attribute signal adds weight to a tag, and a tag applies past its threshold.
- The tag set needs discussing. Starting proposal:
  - **Tank:** Shield, Armor or Hull, and Active or Buffer.
  - **Speed:** Nano (overdrives, nanofibers and polycarbon rigs, with a propulsion module).
  - **Role:** PvP (point, scram or web fitted), Ratting (no tackle, an omni or rat-tuned tank, drone or missile damage), Tackle, Logi, EWAR, Cloaky, Bait, Kitchen-sink.
- Signals we already have: zKill `Labels` on the killmail (`pvp`, `npc`, `solo`, ...) and the Ratters tab logic.
- Tags show on fit list rows and in the fitting window, and the list can be filtered by tag.

**Data crunching comes later.** A debug export writes every fit in the cache to JSONL, to be clustered offline for tuning the rule weights. The app still classifies by rules only.

## Phase 4: dogma engine (resists, EHP, repair, ewar resistance)

- **Approach:** a `fitting` package containing a real dogma engine, not per-stat formulas. It needs:
  - item, location, location-group and required-skill modifiers
  - the nine operations, from preAssign to postAssign
  - stacking penalties, `e^-(n/2.67)²`, applied only to attributes not marked stackable
  - all skills at V
- **Data:** extend the `cmd/sdegen` extract with the attributes, effects and `modifierInfo` the engine needs (decided 2026-10-27: SDE extract, not the ESI).
- **Known traps:**
  - Some CCP effects have no `modifierInfo` (Pyfa hand-codes hundreds of them). Each needs a written case.
  - An abyssal module appears on a killmail as its base type, so its mutated stats can't be known. Flag such fits.
  - The Reactive Armor Hardener starts at an even split.
  - Killmails don't record whether modules were online or active, so assume all are online and active.
  - No heat and no fleet boosts.
  - Implants count only if they are on the killmail. This may become a toggle.
- **Outputs:**
  - resists per layer, with the holes highlighted
  - omni EHP
  - active rep per second, with paste for ancillary repairers
  - peak passive shield regen
  - remote rep output for logi
  - sensor strength and type, plus any `*Resistance` ewar attributes the hull has
- **How they are shown:** to be decided, within the room phase 2 leaves in the fitting window.
- **Proving it's right:** golden tests, a set of reference fits whose expected numbers come from Pyfa, with the Pyfa version recorded. They cover T3s, command ships, Marauders, capitals and logi. The tests fail if any number drifts beyond rounding.
