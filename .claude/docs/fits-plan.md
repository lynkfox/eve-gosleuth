# Fits plan

How victim fits are read, shown, exported, tagged, and (later) analysed. The phases are in build order. When a phase lands, its behaviour moves into `.claude/docs/features.md` and it is struck from here.

## Where things stand

- `retrieval.FitItem` exists and `aggregate` already collects `ShipFlown.Fits` / `Structure.Fits`, but nothing fills `KillmailVictim.Fit`: `RawKillmail.Expand` copies only the raw `Victim.Items`.
- `api.ESIItem` keeps only the name and group. `/universe/types/{id}` also returns `dogma_attributes` and `dogma_effects`, which we discard. Every phase below needs them.

## Phase 1: read the fit from the victim

**Status (2026-10-27): built.** `cmd/sdegen`, `comm/fit_types.go`, `comm/inventory_flags.go`, `retrieval/fits.go`, and `retrieval/eft.go` are written and tested; the CLI prints the target's losses as EFT, and the Fits tab shows them (each entry carries its EFT, so there is no separate App call). Ten exports were imported in pyfa on 2026-10-28 (see EFT export below).

1. **Type data comes from a trimmed SDE extract**, `static_data/fit_types.json`, generated by `go run ./cmd/sdegen` (decided 2026-10-27). For each type it holds the name, group, category, module slot, hull slot counts, and T3 subsystem slot modifiers. Regenerate it when a new SDE adds hulls or modules. A type newer than the extract falls back to the ESI for its name and is placed by its flag alone.
2. **Slot flags go in static data,** as `static_data/inventory_flags.json`. The starting point is the user's flag list from an older project. It gets checked against real killmails and an invFlags dump, since the JSONL SDE no longer ships invFlags. Special holds are named, and they read either as cargo (the ammo hold, the booster bay) or as ignored:

   | Flag | Slot |
   |---|---|
   | 11–18 | Low |
   | 19–26 | Mid |
   | 27–34 | High |
   | 92–99 | Rig |
   | 125–132 | Subsystem |
   | 87 | Drone bay |
   | 158 | Fighter bay |
   | 88 | Booster |
   | 89 | Implant |
   | 5 | Cargo |
   | 164–171 | Structure service |
3. **Module or charge.** A loaded charge has the same flag as its module. The extract gives a module its slot, from the `hiPower` / `medPower` / `loPower` / `rigSlot` / `subSystem` / `serviceSlot` effect. A type with no slot sharing that flag is the module's charge.
4. **Build a `Fit`** in `RawKillmail.Expand`, replacing the flat `[]*FitItem`:
   - It has `Highs`, `Mids`, `Lows`, `Rigs`, `Subsystems`, `Drones` and `Cargo`, plus the hull's slot counts.
   - Merge the destroyed and dropped entries for the same type and flag.
   - Pair each charge with its module.
   - Keep only this cargo: boosters, scripts, nanite paste, charges and ammo. These are group lists in static JSON, extending `ammo_types.json`. Quantities need not be exact.
5. **Slot counts** come from the hull's attributes: `hiSlots`(14), `medSlots`(13), `lowSlots`(12), `rigSlots`(1137) and `serviceSlots`(2056). For a T3 cruiser, add each subsystem's slot modifiers (1374/1375/1376).
6. **Fetch during the search,** never lazily from a tab: only types missing from the extract need the ESI, and they are prefetched before the killmails are expanded.
7. **EFT text first.** `Fit.EFT(title)` is built before any fitting window, and the CLI prints the target's losses as EFT for testing. The fitting window waits until extraction is proven.
8. **Tests:** table-driven, built from real ESI killmail JSON:
   - a T3 cruiser
   - a hull with empty slots
   - a ship with a drone bay
   - a structure
   - one fit whose modules all dropped, and one whose modules were all destroyed

### Decisions from the first real run (2026-10-27)

- **Capsules are not fits.** A capsule loss is left out of the Fits tab. When the same pilot loses a capsule with implants later in the same battle as a ship, those implants belong with that ship loss. Built 2026-10-27: they curve down the window's left side.
- **Nested items are ignored entirely.** Ships in a maintenance bay, ships in an escape bay, and container contents are escape ships, cap-stick trucks, or cargo, so they don't matter here. The ESI item struct already drops them.
- **Modules with no slot in the SDE** (built-in hull weapons such as the Lux Kontos, quantum cores, the moon drill) can be ignored. They are still placed by their flag.
- **Tactical destroyer modes** wait for phase 4, where they change live stats.

## Phase 2: Fits tab, fitting window, and EFT export

**Status (2026-10-27): built,** as described in `.claude/docs/features.md` under Fits. Not yet done: importing several exports in-game. The phase 4 numbers go in a strip under the ring (decided 2026-10-29).

### Which searches

- Pilot, corporation and alliance searches get a **Fits** tab.
- System searches do not.

### Tab layout

**Left: the fit list**

- A scrolling list of the target's losses with a fit, grouped by hull.
- Each row shows the date and the system, with the fit's tags on a line beneath, under a heading for its hull. Who lost it is in the fitting window (pilot names left the rows 2026-10-28).
- A count marks identical fits merged into one row. Two fits are identical when they have the same hull and the same modules in each slot group, whatever the charges or cargo.
- Corp and alliance searches merge identical fits across pilots, grouped under the ship (decided 2026-10-27).

**Right: the fitting window**

- One fitting window, rebuilt in place whenever a row in the list is selected. It is a pane of the tab, not a popup.
- The hull render (`images.evetech.net/types/{id}/render`) is in the centre, with slot icons around it:
  - highs on the top arc, mids on the right, lows on the bottom
  - rigs and subsystems on the inner left
  - an empty slot is drawn as a hollow socket
  - a loaded charge is a small badge on its module
- Drones, fighters, and the kept cargo are listed below or beside the ring.
- The ring is positioned with CSS trig, so no new libraries. Names are set with `textContent`.
- An **Export EFT** button sits in the window's header (see EFT export).
- The phase 4 numbers (resists, EHP, repair, ewar) go in a strip under the ring (decided 2026-10-29).

### Getting to a fit from elsewhere

- Killmails get **no popup**.
- The killmail row's right-click menu gains **"Show fit"**. It switches to the Fits tab, selects that killmail's fit in the list, scrolls it into view, and rebuilds the fitting window.
- The item appears only when the victim is the target or one of its holdings and the loss has a fit.
- Per the right-click menu rule, the item gets no help text of its own.

### EFT export

- The button copies the fit to the clipboard through the Wails runtime.
- The text is built in Go (an `App` method), so it can be unit-tested. In order:
  1. Header `[Hull, GoSleuth - Pilot - KM#]`.
  2. Lows, then mids, highs, rigs and subsystems, with a blank line between groups.
  3. `Module, Charge` for a loaded module, and `[Empty Low slot]` (and so on) for an empty slot.
  4. Drones as `Name xN`.
  5. Cargo as `Name xN`. Boosters go here too, since the in-game importer is fussier about a separate booster section.
- Check several exports by importing them in-game before calling this done.

**Import check (2026-10-28, pyfa).** Ten scenario exports, built by `Fit.EFT` from made-up killmail items. The header, empty slot lines, T3 subsystems and slot counts, scripts, crystals and cap charges, quoted and faction names, booster stacks in cargo, merged drone stacks, and loaded probes and interdiction spheres all imported correctly. Two outcomes are accepted as they are:
- A dread's charges (Moros, Void XL) went into cargo rather than the guns.
- A mutated (abyssal) module is left as an empty slot. A killmail names only its type, and pyfa and the game both drop it. Players know this.

## Phase 2b: finding and folding fits

- **A filter box** above the fit list. Built 2026-10-28: each word must match the hull, a module, or a loss's pilot, corp or alliance name, and the words after "tag:"/"tags:" are tags a fit must have. A ? to the box's left explains it. Hull headings with no match left are hidden. Still open: the system, and charge, drone or cargo names.
- **Merge fits whose modules differ only by name.** Since tiericide, many modules with different names have the same stats and meta level, such as the named T1 variants within one meta group. Two fits merge when each pair of differing modules shares the same group, meta group and meta level, and the same dogma attributes.
  - The equivalence comes from the `cmd/sdegen` extract: an `equivalent` id per module, or a list of equivalence classes, worked out at generation time. The app does no attribute comparison itself.
  - The merged row shows the most common name for each slot and says that variants were folded in. The fitting window shows the selected loss's own modules.

## Phase 3: tags

**Decided 2026-10-28.** **Status (2026-10-28): scoring built.** `comm.LoadFitTagRules` loads the rules (merged over by an edited copy like the other files), `retrieval.Fit.Tags()` scores them, and `gui.FitLoss.Tags` / `FitGroup.Tags` (its first loss's) carry them to the frontend. The Fits tab shows them (see features.md) and the user guide covers the file. Fleet Doctrine built 2026-10-29 (see features.md), as was the rats-on-the-killmail nudge toward Ratting. Not yet done: tuning the weights against real fits.

Tags describe what a fit brings, for intel: what it shoots with, how it tanks, and what it is for.

### Rules

- The rules live in `static_data/fit_tag_rules.json`, so they can be tuned beside the exe without a rebuild.
- **Weights and thresholds.** Each signal (a module group, market group or type, fitted or counted) adds weight to a tag, positive or negative, and the tag applies once its total passes the tag's threshold.
- Each tag remembers which modules gave it weight, so the fitting window can say why it applied ("Tackle: Warp Scrambler, Stasis Webifier").
- **Data:** groups alone can't tell pulse from beam, blaster from rail, autocannon from artillery, or a sentry from other drones. `cmd/sdegen` adds each type's market group to `fit_types.json` (built 2026-10-28: `market` per type, a `market_groups` parent map, `comm.InMarketGroup`), and rules can match a market group or any of its parents. Checked 2026-10-28: the market tree splits all four (Pulse 558 / Beam 557, Blasters 556 / Railguns 555, Autocannons 559 / Artillery 560, Sentry Drones 911). Only mutated modules, a few Civilian items, and the Lux titan weapons have no market group; match those by group. Phase 2b and phase 4 extend the same extract.
- **The rules** (drafted 2026-10-28) are in `static_data/fit_tag_rules.json`. A weight is about one slot given to that job. A signal matches modules and drones by `types`, `groups`, `categories` or `markets`, or the hull with `hull: true`; each matching item adds its `weight`, up to the signal's `max`. A tag's `requires` must each match at least once (Nano needs a propulsion module), and none of its `forbids` may match (Logi: no turrets or launchers, so a spider-tanking gun ship isn't logi). `hull_sizes` limits a signal to hulls of those rig sizes (a heavy neut on a cruiser). `bonused_by` lists words: on a hull with a bonus line containing one, each match adds `bonused_weight` instead (a Blood Raider hull's neuts count more; one without neuts gets nothing). Matching ignores case, and skips bonus lines containing a phrase in the file's `bonus_ignores` ("resistance", "immune to", ...), which name what a hull resists rather than what it uses. `note` is for people only.
- **Hull bonuses** (2026-10-28): sdegen keeps each hull's `rig_size` (attribute 1547) and `bonuses`, its role and skill trait lines from typeBonus.jsonl as text without markup or numbers (about 160 KB). Text, not the skill ids the traits link: a skill covers more than the bonused module (the Ashimmu's web bonus links Propulsion Jamming, which scrams also use), and some useful lines link nothing ("bonus to Armor Plates and Shield Extenders").
- **Rack share**: thresholds use the raw weights, so three neuts is three neuts on any hull. Each tag also has a `share`: each module adds its weight divided by the slots in its rack (the hull's, with subsystem modifiers); hull and drone signals divide by the hull's average of high, mid and low slots. It no longer ranks tags (priority does); `share_threshold` uses it, ie Firewaller's 0.75: smartbombs aren't limited by hardpoints, but a firewaller may keep a slot or two for something else. Singular modules (one to a ship: Vorton, Disintegrator, Bastion, cyno) are never marked down, as only Firewaller uses share; their tags' thresholds are 1 (Vorton's was 2, fixed 2026-10-28).
- **Drones are a weapon** (decided 2026-10-28): combat drones count toward Drones, Close and Long, never toward a role. **Changed 2026-10-29:** a killmail lists only the drones left in the bay, not those in space, so drone signals are `once` (a kind of drone being there counts, not how many), and a hull bonused for drones (`bonused_by` on a zero weight hull signal) is what makes Drones, and a carrier's launch line Fighters. Support drones (sensor damp, tracking disruptor and painter drones toward EWAR, EC drones toward ECM, neut, web and logistic drones toward theirs) are a nudge like implants, never a role on their own. `bonus_ignores` gained "penalty to" and "reduction in Drone hitpoints" (the Griffin Navy Issue's drawbacks). The general drone phrases start "to " ("to Drone hitpoints"), so the Geri's and Bestla's "Stasis Webifying Drone hitpoints" doesn't make them drone hulls; `bonus_ignores` can't be used for that, as Webber reads those lines.
- **Shared priority** (2026-10-29): tags may share a priority, the one furthest past its threshold (weight ÷ threshold, or share ÷ share threshold) first, then name (`sortFitTags`, `passedBy`). Prompted by a Lachesis with three points and one bonused damp named EWAR.
- **Priority** (decided 2026-10-28, replacing ranks by rack share; final order set later that night): each tag has a `priority`, and every shown tag is a `role` that may name the row. Order: Polarized (added 2026-10-29: any of the 12 polarized weapons, a special case that always names the row), Fleet Doctrine, Ratting, Logi, Roller (moved above Links 2026-10-29, so a capital roller with bursts is a roller), Links, Bubbler, Cyno, Bait, Neut, EWAR, ECM, Firewaller, Tackle, Nano (moved below Tackle and EWAR so interceptors and recons aren't named Nano), Webber, Scanner, Cloaky, then the tank tags (Shield, Armor, Hull, Active, Buffer, Passive). Roller sits high so rollers don't read as ECM, Tackle, Bait or Links. The first role names the row and the next three shown tags go beneath, all as full words (no letters, Abyssal and Implants included).
- **Tag weights** (2026-10-28): a rule's `tag_weights` add weight for other tags the fit has, scored after the exclusive tank style is settled, so they read only tags without `tag_weights` of their own. Ratting has Buffer -5 and Passive -5 (softened to -1 on 2026-10-29, as passive Gilas and Ishtars rat): a buffer or passive tank is rarely a ratting fit. Active +0.5 with the bastion at 1.5 (2026-10-29, a torp Golem with an X-Large booster and no point read as only EWAR): a bastion with an active tank and no point is Ratting. A marauder hull (group 900) adds 0.5 (same day), so a marauder in bastion is Ratting unless a point, ancillary repairer, or cap booster (-1 each) or a buffer tank counts against it.
- **Reasons** are structured (`FitTagReason`: name, count, weight), adding up to the tag's weight (a capped signal's matches share the cap), and the tag carries its `threshold` and `share_threshold`, for the fitting window's tip.
- **Capitals, subsystems, implants** (2026-10-29): a capital (hull size 4) is never Nano or Cloaky, by a hull signal naming no types (it matches any hull of its sizes). A T3 cruiser's fitted subsystems' bonus lines count as its hull's for `bonused_by`. Implants from the capsule lost with a ship are parts the signals see: Snake toward Nano, Crystal and Nirvana toward Shield, Amulet and Asklepian toward Armor, 0.1 each capped at 0.5 a signal, a nudge for a fit just short. Ascendancy (warp speed) was left out of Nano, and Active needs no nudge as any repairer makes it.
- **Weapon tags are hidden** (decided 2026-10-28): Lasers, Hybrids and the rest, and Close and Long (tags of their own), are weighed and filterable but never shown in the list or the key and never name a row. Changed 2026-10-29: the fitting window shows them last, muted, with their weights on hover.

### Tag set

- **Weapons:** Lasers, Hybrids, Projectiles, Missiles, Drones, Fighters, Vorton, Disintegrator. Each also gets **Close** or **Long**:
  - turrets by market group (pulse, blaster, autocannon are Close; beam, rail, artillery Long)
  - launchers by group (rockets, heavy assault missiles, torpedoes Close; light, heavy and cruise missiles Long)
  - drones: sentries Long, the rest Close.
- **Tank:** Shield, Armor or Hull, and Active, Buffer or Passive (shield regen). No resist profile tags (omni or tuned). Active, Buffer and Passive are **exclusive** (decided 2026-10-28), the first exclusive set (Polarized over Ratting added 2026-10-29, applied again after tag_weights as Ratting has them): the file's `exclusive` lists them, and the first listed the fit has applies alone, Active, Passive, Buffer (changed from heaviest-wins the same night: any repairer makes a tank active, however much buffer). Active needs a repairer, not just amplifiers or rigs. Layers can mix, so a fit can be Shield and Armor.
- **Movement:** Nano only (overdrives, nanofibers, polycarbon rigs, with a propulsion module).
- **Roles:** Tackle, EWAR and ECM (1.5 from 2026-10-29: one module on a hull bonused for it, ie a single damp Lachesis, or two anywhere), Webber (added 2026-10-28: web-bonused hulls such as the Vindicator and Huginn fill their own role; webs still count a little toward Tackle), Roller (added 2026-10-28: a Higgs anchor rig of any size, two or more zero-point mass entanglers on a HIC, or two propulsion modules on a battleship or capital), Bubbler (was Bubbles), Logi, Links (command bursts, added 2026-10-28), Firewaller (a full high rack of smartbombs, added 2026-10-28), ECM, EWAR, Neut, Cloaky, Scanner,  Cyno, Ratting (a bastion module with smartbombs counts too, 2026-10-28: probably PvE). **Scanner** (replaced Probes 2026-10-28): a probe launcher with any scanning array (or two arrays), or any relic or data analyzer. **Cyno** (one tag for every cyno, covert and industrial included, 2026-10-28) applies with a single generator. It first always named the row; the priority list later that night put it seventh. Kitchen-sink was dropped 2026-10-28: in game it describes a doctrine where everyone brings what they like, not a ship.
- **Bait**, a narrow weighted rule:
  - a heavy buffer; a hull tank (bulkheads, hull repairers) weighs most
  - little or no damage weighs for it
  - tackle adds a little but isn't needed
  - a cyno counts for nothing.
- **Fleet Doctrine**, the one tag that reads more than the fit. A fit gets it if either rule holds (widened 2026-10-28):
  - **In one battle:** a loss qualifies when its battle (`aggregate.CollectedData.BattleOfKillmail`) has at least 5 ships of its hull on the victim's side, and logi there too. The victim's side is the target and its holdings in that battle, from their kills and losses there; the enemy flying the same hull doesn't count. A merged fit gets the tag if any of its losses qualifies.
  - **Across battles:** the same fit (one merged row, `fitKey`) was lost at least 5 times within one alliance, by at least 5 different pilots, in any battles. Losses count by the victim's alliance at the time, not their corp, so pilots of different corps in one alliance add up; the target's holdings count as one with it.
  - Every number (the battle's hull count, the logi needed, the losses and pilots across battles) is in `fit_tag_rules.json`.
  - The logi hulls are `logi_groups` and `logi_types` in `ships.json` (2026-10-29: T2 logi, logi frigates, force auxiliaries, and the eight T1 logi cruisers and frigates). The victim's side is the target and its holdings plus the victim's alliance, or corp outside one, so a pilot target's fleetmates count.
- **Rats on the killmail** (2026-10-29): an `npcs` signal matches the NPC attackers on a loss's killmail (`Fit.TagsWith(FitTagContext)`), not the fit. Ratting counts them `once` at 1, the user's choice: a nudge that needs another PvE sign. Gate and station sentries (99), CONCORD (301), police (182), and faction navies (288) are `npc_not_rat_groups` in `ships.json`, matched by the ESI group of the NPC's ship as the extract has no NPCs; site sentries (383) stay rats. The Ratters tab skips them too.
- Other tags are read from the fit alone. zKill's `npc` and `solo` labels belong to single losses, so they don't make tags.

### Showing tags

- **A fit can have many tags** (decided 2026-10-28). The fitting window shows every tag of the fit, with the reasons on hover.
- **The fit list** (built 2026-10-28): the fit's first role by priority names its row, and the next three shown tags are pills on the line beneath, with Abyssal and Implants. The filter still finds every tag. The key in the tab's help explains each.
- **The list is filtered by tag** in the filter box, by name or its start after "tag:"/"tags:" (`filterFits`, `fitTagNamed`), or by clicking a tag.

**Data crunching comes later.** A debug export writes every fit in the cache to JSONL, to be clustered offline for tuning the rule weights. The app still classifies by rules only.

## Phase 4: dogma engine (resists, EHP, repair, ewar resistance)

**Status (2026-10-29): built,** the same afternoon it was planned, by the agent split below (extract, engine core, effects & outputs, golden; then the strip). `go test ./fitting` checks 37 Pyfa fits; 34 match within 0.1% and 3 are known differences (below). Its behaviour is in `features.md` under Fits.

**Planned 2026-10-29.** Two research passes went into it: one over the SDE (build 3660036) and one over Pyfa's engine (`eos`, v2.69.3, commit d2722a4c). Their notes are kept with this plan's history. Pyfa is GPLv3 and this project is MIT, so Pyfa is read for reference and used to produce test numbers, and none of its code is copied.

### What the research settled

- **A generic engine, not hand-written effects.** 3,210 of the SDE's 3,427 effects carry `modifierInfo`. Pyfa ignores that and writes every effect by hand: 2,426 classes in a 44k-line `effects.py`. We read `modifierInfo` instead, and write only what it can't express.
- **What needs hand-written code is small:**
  - local reps: shield boosting (4), armor repair (27), hull repair (26)
  - ancillary reps: armor (5275), whose paste multiplier is the SDE's `chargedArmorDamageMultiplier` (1886) and not Pyfa's hard-coded 3, and shield (4936), which gets no charge multiplier
  - the Reactive Armor Hardener (4928)
  - remote reps for logi: shield 6186, armor 6188, hull 6185, ancillary 6651/6652, mutadaptive 7166, and capacitor 6184
  
  Damage Control, Assault Damage Control, Bastion, Siege, Triage, the tactical destroyer modes and the T3 subsystems all work from `modifierInfo`.
- **Corrected while building:** the research was wrong here. Skills scale 400 of the 415 hull bonus attributes themselves through their own effects (ie Battlecruisers multiplies `shipBonusCBC2` by its level), and scaling those again zeroed a Drake's shield resists. `bonus_skills` now holds only the 15 no skill scales (sdegen's `skillScaledAttributes`), ie the assault frigates' `eliteBonusAssaultShips1`.
- **Hull bonuses scale with skill level, and the SDE doesn't say which do.** A hull's bonus attribute (ie `shipBonusMF`, 587) has to be multiplied by the level of its skill, and a role bonus is not. Pyfa hard-codes the skill in 1,378 places. Attribute names carry the skill, so `shipBonus<race><class><n>`, `eliteBonus<class>` and `subsystemBonus<race><kind>` (414 attributes) can be read by `cmd/sdegen` into a bonus-attribute-to-skill table in the extract. `typeBonus.jsonl` trait values back it up, and sdegen reports the ones it can't place, for its own config. A dev check compares the table with the `skill=` arguments in Pyfa's `effects.py`.
- **Skills are ordinary dogma.** Each skill scales its own bonus by `skillLevel` (280) with an `itemID` modifier. All V means attribute 280 is 5 on every skill. That needs the 512 skills (category 16) and the character type (1373) in the extract.
- **Size is no concern.** An extract trimmed to the attributes our outputs depend on is about 0.8 MB (100 KB gzipped). That covers 7,904 types and 1,141 effects, with modifiers on `targetID` dropped. Adding the 2,144 unpublished types in the kept categories brings it to 1 MB. Those include expired boosters, retired modules, and the 18 tactical destroyer modes (group 1306, needed).

### Engine rules

- **The nine operations, in dogma order:** preAssign (-1), preMul (0), preDiv (1), modAdd (2), modSub (3), postMul (4), postDiv (5), postPercent (6), postAssign (7). Pyfa skips preDiv, postDiv and postAssign, and does a preMul after adds. We implement all nine, so where a golden number differs for that reason, the test records the reason rather than copying the error.
- **Lazy, dependency-ordered evaluation.** An attribute is computed when first read, from its sources' own computed values, and cached for the fit. This replaces Pyfa's early/normal/late run order. Assault Damage Control works without special code: its active effect assigns the module's own resonances, and its online effect then applies them to the ship. The same goes for Triage changing a remote rep's amount before the rep is read.
- **Caps:** an attribute with `maxAttributeID` is capped by that attribute, so resonances never go above 1.
- **Stacking penalty:** `1 + (m-1)·e^-(i/2.67)²`, with i from 0. Bonuses and maluses form separate chains, each sorted by the size of `|m-1|`, largest first. A modifier is penalized when all of these hold:
  - its attribute is `stackable: false`
  - its operation multiplies (pre/post Mul, Div, or Percent)
  - its source is not a hull, skill, implant, booster or subsystem
  
  A chain is per attribute and per stage, so pre-stage modifiers (Damage Control, Reactive Armor Hardener, Bastion) penalize each other but not the post-stage hardeners. The golden fits decide whether charges are exempt too.
- **Module state:** a module's effects apply by category: passive (0) always, online (4) online or higher, active (1) when active, overload (5) never (no heat). Effect 16 `online` is category 1 but marks being online. Killmails don't record state, so every module is active, Assault Damage Control included, and the window says so.
- **Domains:** `shipID`, `charID`, `itemID`, `otherID` (a charge and its module), and `structureID`. `targetID`, `target` and `EffectStopper` are skipped, since nothing is projected.
- **What counts:**
  - implants only if they're on the killmail, ie those from the capsule lost with the ship (`podsWithShips`)
  - boosters in cargo don't count
  - no fleet boosts and no heat
  - a mutated module counts at its base type's stats, and the window says so, as its rolls are not on the killmail
- **Ships first.** Upwell structures (security-scaled rigs, services) come after ships work.

### Decisions (2026-10-29)

- **The numbers go in a strip under the ring,** between it and the drones and cargo:
  - a four-column resist grid per layer, with the holes highlighted
  - omni EHP
  - local rep/s (with paste for ancillary repairers) and peak passive regen
  - remote rep/s for logi
  - sensor type and strength
  - the hull's EWAR resistances
  - a line naming what was assumed (all modules active, the Reactive Armor Hardener settled against uniform damage, the mode)
- **The Reactive Armor Hardener is simulated against uniform damage,** as Pyfa does it, up to 50 cycles, moving `resistanceShiftAmount` from the weakest-hit type each cycle. A repeating loop is averaged and rounded to 3 places. It applies in the pre stage, so it penalizes against Damage Control.
- **Tactical destroyers get a mode switch.** All three modes are computed during the search (the Stats travel per mode), and the strip has Defense/Sharpshooter/Propulsion buttons that start on Defense.
- **Golden numbers come from a headless Pyfa,** run by an agent in the scratchpad: build its `eve.db`, import each EFT with `service.port.eft.importEft`, and read `fit.ehp`, `fit.tank`, `fit.getRemoteReps()` and `fit.scanStrength`. If wx blocks that, the user enters the fits in the Pyfa GUI instead. About 30 fits cover:
  - T3 cruisers and tactical destroyers in each mode
  - command ships, Marauders in Bastion, dreads in Siege, and a FAX in Triage
  - T2 logi and a logi frigate
  - Damage Control and Assault Damage Control stacked with hardeners, the Reactive Armor Hardener, and ancillary reps with and without paste
  - a passive shield fit and a hull tank
  - a fit with implants
  
  Each file records the Pyfa version and the build of Pyfa's own data, since it may lag our SDE. The tests fail when a number drifts beyond rounding, unless the file names a known difference.

### Contract (written first, by me)

- **`comm/dogma.go`:** `DogmaFile` is the loaded `static_data/dogma.json`, holding `sde_build` and:
  - `attributes`: id → default, stackable, highIsGood, maxAttributeID
  - `effects`: id → category, duration/discharge attribute ids, and modifiers (domain, func, modified, modifying, operation, group, skill)
  - `types`: id → attributes and effect ids, with its default effect
  - `bonus_skills`: bonus attribute id → skill type id
  
  It is loaded by `comm.InitStaticData` as the other files are, and an override replaces a type or effect whole. A placeholder file covers a Rifter and one module for the engine's tests. If `sde_build` differs from `fit_types.json`'s, the app logs a warning.
- **`fitting` package (new):**
  - `Input`: the hull, `[]Module{Type, Charge, Slot}`, implants, and a T3D `Mode`
  - `Compute(Input) (*Stats, error)`
  - `Modes(hull) []int`
  - `Stats`: the layers (HP and four resonances each), omni EHP, local rep/s, passive regen, remote rep/s, sensor, EWAR resistances, `Assumptions`, and `Unknown` (types not in the extract)
  
  It doesn't import `retrieval`. A small adapter turns a `retrieval.Fit` into an `Input`. The interface between the engine core and the hand-written effects is `engine.Attr(item, attrID) float64` plus a table of hand-coded effects keyed by effect id. Every exported name is stubbed so it compiles before any agent starts.
- **`gui.FitLoss.Stats`:** `[]ModeStats` (one entry with no mode, or three for a T3D), filled during the search like `Tags`, never lazily.

### What the golden fits found (2026-10-29)

- Hull bonuses scaled twice (above): 23 of 38 fits failed, then 8.
- Implant sets: a set's bonus reaches the other implants through the character's location, which the engine first left implants out of.
- **Bastion's hull resists aren't stacking penalized** against a Damage Control, as Pyfa has it (user's call: follow Pyfa). That is the `unpenalized` list in `dogma.json`, written by sdegen's `unpenalized`, read by `comm.DogmaUnpenalized`.
- The harness wrote a Herald with a placeholder hull id; that fit was dropped.
- **Known differences** (in the golden files): the Damnation and Vulture, as Pyfa applies a fit's own command bursts to itself; and a Reactive Armor Hardener with a Damage Control and a hardener settles 0.13% from Pyfa on thermal, not yet explained.
- Regenerating: the harness is in `fitting/testdata/golden/harness/` (`SETUP.md` there: a Pyfa checkout, a venv, and Pyfa's `db_update.py`, none committed). Regenerating keeps the known differences.

### Next: own boosts, with a button (user's call 2026-10-29)

- A command ship's bursts reach itself in game, and Pyfa counts them. The user wants **a button in the fitting window to turn the fit's own boosts on and off**.
- The SDE gives bursts no modifiers, but `dbuffCollections.jsonl` defines each warfare buff (what it modifies, how, and which aggregate mode), and a burst charge names its buffs with `warfareBuff1ID`..`4ID` and their values. So bursts can likely be data-driven: sdegen extracts the buff collections, and the engine applies a fit's own active bursts' buffs to its ship when the button is on, keeping the strongest of each buff as the game does.
- The stats then travel twice (with and without boosts), or per mode and boost for a tactical destroyer, and the Damnation and Vulture golden fits lose their known difference.
