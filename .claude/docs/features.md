# Features

How each feature works, for when you are changing it. The rules that apply everywhere are in `CLAUDE.md`.

## Search bar

- The search bar has no type: `SearchTarget(name, "")` looks the name up with `retrieval.MatchTargets` (ESI universe/ids: exact names ignoring case, plus corps and alliances by ticker, ie Jita Holding Inc. (JITA) for Jita, kept as `ByTicker` since a player may only have seen a ticker; items left out) and searches a lone exact match, or with more than one or any by ticker returns `TargetResult.Choices`, ticker ones last, for `chooseTarget` (main.js, `#target-choice`) to ask which, then is called again with the chosen name and type. A typed lookup (`GetTargetInfoOfType`) prefers the exact name among its type.
- A name filled in by the app, ie a recent search or a menu's Search, carries its type and eve id as `searchTypeHint`/`searchIdHint`, cleared by typing, and `SearchTarget(name, type, id)` then looks it up by id (`GetTargetInfoByID`, `lookupTargetByID`), with no name lookup: the ESI's universe/ids can not find every name, ie the alliance L A Z E R H A W K S. Pass the id wherever a search is offered; recent searches save it (`RecentSearch.ID`) and the holding redirect uses the main's.
- A zKillboard or EveWho link typed into the search bar, My Intel, or the holding dialog is read by `api.ParseEntityLink` and looked up by its id, its own type winning over a dropdown's where that kind is allowed (`lookupEntity`).

## Recent searches

Recent searches live in the cache, not settings (retrieval/recent_searches.go): `SearchTarget` calls `AddRecentSearch` with each found target as EVE spells it, with a corp's or alliance's ticker (`TargetDisplay.Ticker`, also on `RelatedEntity`, shown EVE style, [CORP] and <ALLY>, by `formatTicker`; a typed ticker finds its recent search), one `Permanent` row per search in the `recent_search` section keyed by type and lower case name, keeping the number set in Preferences (`Preferences.MaxRecentSearches`, default `DefaultRecentSearches` 5, at most `MaxRecentSearches` 25; lowering it calls `TrimRecentSearches`); the × on a row calls `RemoveRecentSearch`. An SDE release keeps them; Clear everything and Clear older than remove them. The page asks for them as it loads, which waits for startup to load the cache (`App.waitReady`, see CLAUDE.md).

## Search limits, caveat warning, collapse target

- The search limits button beside the search bar (`#limits-button`, gui/search_limits.go) changes what searches collect (max, pages, newer than, cached, holdings) until the app closes: `SetSearchLimits` keeps them on `App.searchLimits` (under `settingsMu`, so it skips `a.mu`), `searchPreferences()` is the Preferences with them in place and is what `CollectIntel` and `holdingMain` read, and `SaveSearchLimits` makes them the defaults; the button is in the accent while it has its own.
- The Collapse target on search preference (`Preferences.CollapseTarget`) pulls the target panel shut at each search.
- The pull bar under the target panel steps it shut: for a target with holdings saved, the first click puts the holdings away and the next shuts the panel; without any, one click shuts it. A click from shut opens it all (`stepTargetPanel`).
- As the app launches, `showCaveatWarning()` opens the killmail caveat warning (`#caveat-warning`) while `Preferences.ShowCaveatWarning` (on by default) is on; its Don't show this again box calls `DismissCaveatWarning`.

## Stopping a search

`StopSearch` (gui/search_control.go) halts the ESI `RateGuard` (`api.ErrStopped` for every request), so killmail collection ends where it is and the report is built from what is cached; `SearchTarget` and `CollectIntel` resume it when they return, and the report's `stopped`/`rateLimited` flags show a warning above it. A search asks the frontend a question with `ask` (a Wails event) and waits for `AnswerPrompt`. Closing the app during a search stops it the same way (`shutdown`), refuses any search asked for after (`errAppClosing`, so a queued one can not undo the stop), and waits until `shutdownSearchWait` (5s) has passed for it to let go of `a.mu` and a check of imported entities `checkMu` (`lockBy`); past that it saves and closes the cache without them, so the process never lingers windowless until the search ends. Shutdown keeps both locks, as nothing may start after the cache is closed. A cache save is one SQLite transaction (WAL), so even a killed process keeps the cache as last saved.

## Debug mode

Debug mode (`Preferences.DebugMode`, gui/debug.go; in Preferences under Advanced, a `<details>` with Game data that `openPreferences` closes each time, Debug mode's and Game data's descriptions in `<template>`s opened by the filled i before their names (`.preference-more`) in `#preference-more`, Game data's linking the user guide `docs/static-data-overrides.md` on GitHub) lasts until the app closes (`loadSettings` and `shutdown` turn it off) and puts an orange border round the window (`body.debug-mode`, `showDebugMode`): the log goes to Debug level, and `debugRecorder`, a logrus hook, writes each search's entries to `debug/search-<time>.log` beside the settings, from `SearchTarget` (`startDebug`) to the end of `CollectIntel` or a failed `SearchTarget` (`finishDebug`, deferred before `recoverAsError` so panics are in it). It is then zipped with `session.json` (build, OS, WebView user agent, preferences, effective search limits, the search, cache counts, static data overrides with hashes, memory), the newest 256 KB of `crash.log`, `frontend.log`, and `goroutines.txt` into `gosleuth-debug-<time>.zip`, the newest 10 kept; a log left by a search the app closed during is zipped at the next start. `crash.log` is trimmed to its newest 512 KB past 1 MB. The frontend's JS errors reach the log through `LogFrontendError`; in debug mode one made between searches (`keepFrontendError`) is appended to `debug/frontend.log` (trimmed to its newest 256 KB of whole lines once past 512 KB), which the next bundle moves aside under the lock and holds the newest 256 KB of (put back if the bundle fails), so an error after a search ends, ie in a tab, comes with the next search's bundle.

## Killmail collection (`CollectKillmails`)

- Fetches the zKill list newest first, pages of 200 up to zKill's 100; a page short of 200 ends it, except a nearly full page 1 (`zkillNearlyFullPage`), since zKill holds back the newest killmails, under five minutes old, and the page after it failing is then the end of the list; a killmail listed twice is kept once.
- zKill sends the whole ESI killmail with each entry (`ZkbResponse.Killmail()`), so each killmail is the cache's copy, else zKill's (then cached with `StoreKillmail`), else fetched from the ESI; the ESI is only asked for an entry missing its time, system, victim's ship, or attackers, at most `MaxESIKillmails` (1700) a search, the rest skipped with `ErrTooManyESIKillmails`. Only the entries within Max are looked up in the cache, all of them with `IncludeCached`.
- Paging also stops at the page reaching `NewerThan`; when even the newest killmail is older, `ConfirmIgnoreDate` is asked up front and a yes lists again further back.
- Each entity's list is cached (retrieval/zkill_lists.go, section `zkill_list`, gzipped, `Permanent`): `KnownZkillList` keeps zKill's data for each killmail and how many from the top are `Unbroken` (no gap), and every killmail zKill sends, past the limits too, is cached with `StoreKillmail` as it is listed. `listEntity` stops paging at the first page reaching the cached list's unbroken part (`ZkillPaging.Known`) and splices the rest in; when the search needs more than is unbroken it carries on from there (`ZkillPaging.StartPage`). Entries past the limits that only the cached list has are used only with `IncludeCached`. Late-posted old killmails deep in a list are not picked up by a search that stops early.
- A zKill list can be narrowed with `ZkillPaging.Filter` (modifiers put before the entity, ie `losses/groupID/1657`; an entity with a `groupID` means that entity's own ship or structure is in the group), cached apart by `zkillListKey` with the filter.
- This produces `[]RawKillmail{Zkillmail, ESIKillmail}`, and the names, pilots, corps, and the rest the killmails refer to are looked up in bulk afterwards (`PrefetchKillmailEntities`).
- `KillmailLimits` decides how many: a max count (default `DefaultKillmailLimit`, 20, up to 20,000; zKill is paged only until that many are listed), or `AllKillmails` (-1) for every killmail on the first `Pages` pages (default `DefaultKillmailPages`, 10), an optional cutoff date, and whether to also use cached killmails beyond those limits. The GUI takes these from the Preferences window (`gui/settings.go`); the CLI uses `DefaultKillmailLimits()`.

## Allies

- `GetTopAllies` (aggregate/allies.go) feeds the Allies tab (labelled "Allies?", with a note that they are potential allies, not confirmed) of pilot, corp, and alliance targets: the alliances, then corps in no alliance, on the target's kills (not its losses) outside the alliance it was in at each kill, each noting how many of the target's kills its own pilots were the victim of.
- The user can ignore allies per target from a row's right click menu, saved at once by gui/allies.go `SaveIgnoredAllies` in the cache's `ignored_ally` section (retrieval/ignored_allies.go); the × on an ignored one under the table brings it back. `GetTopAllies` skips them so the next ones take their places. The ignored tags show the kills each shared (`AllyRanking.IgnoredKillmails`), most first.
- With the Hide killed allies preference (`Preferences.HideKilledAllies`) every ally the target also killed is skipped too; `RankAllies` re-ranks the shown search after that preference changes. While it is on and the target killed any (`AllyRanking.KilledAllies`), a toggle tag in the theme's accent leads the left-out tags under the table and re-ranks with `showKilled` to show or hide them for that search only (kept on `alliesSource` until the next search).
- Allies leaves out holdings linked to the target's own groups, and skips `internal` killmails.

## Right click menus

Every row's menu is built by `withMenu` in main.js from sections (`openSectionsMenu`): a heading per entity on the row, ie the pilot, their corp, and alliance, each with Search and site links, so rows send corps and alliances as `EntityRef`s. An Allies row's section has its own items above them: Add as Affiliate, Ignore, and Open shared killmails on zKillboard (`AllySummary.TogetherURL`, `api.ZkillTogetherURL`: one zKill advanced search, the target and every holding searched in Attackers as or, the ally in Either, so its kills with them and their kills of it). A killmail card's menu has only the part right-clicked (`killmailCardSections`): the victim, the final blow, or else the system.

## Holdings

- Users see them as **affiliates** (renamed 2026-10-29): every GUI string, help line, progress message, error the frontend shows, and `docs/` say affiliate, while the code, JSON fields, CSS ids, the `holding` cache section, and the My Intel export format keep "holding". Write new user-facing text with affiliate. Systems (home hole, staging) are planned to join them later.
- Holding links (retrieval/holdings.go, section `holding`, gui/holdings.go) tie a corp or alliance to holding corps or alliances by hand; the target panel shows them from both ends (`TargetResult.Holdings`).
- With the Include holdings preference (`Preferences.IncludeHoldings`, on by default) a corp or alliance search sets `IntelTarget.Holdings` to its own holdings (one level, not the mains it holds for): `CollectKillmails` (`listKillmails`) pulls each holding's zKill list with the same paging and merges them newest first, a killmail on two lists kept once as the main's, before Max and the date limit apply. `RawKillmail.Via`/`Killmail.Via` name the holding a killmail came from, shown as a "via" tag at the foot of its card's victim corp and alliance column, on the date's line.
- Searching a holding, while that preference is on, searches its main instead (`holdingMain` in gui/app.go, the first main by name; `TargetResult.SearchedHolding` names the holding for the status line).
- The Allies tab of a corp or alliance opens with a line of its holdings and the kills each shared with it (`aggregate.HoldingKillsTogether`: kills with pilots of both the main itself and the holding).
- Holdings count as the target everywhere through `IntelTarget.IsGroup(corpID, allianceID)`: losses, members, capital pilots, and allies; the Members tab's roster stays the main corp's.
- A killmail whose victim and every attacker are the target or its holdings (`aggregate.IsInternal`, any outside attacker or NPC makes it a normal loss) has the outcome `internal`: still a loss, never a kill.

## Killmails tab

- Kills, Losses, All buttons over the list (`#killmail-filter`, `killmailFilter`, `shownKillmails`) show one side, an internal killmail counted as a loss, with each side's count on its button; the pager pages the filtered list. They are hidden when no killmail has an outcome (a system search), and set back to All on each search.

## Battles tab

- Every target type has it. `buildBattles` (gui/battles.go) turns `CollectedData.BattlesFought` (`aggregate.FindBattles`, battles of more than one killmail) into rows, newest first: its first and last killmail times and length, its main system (the one with the most of its killmails, the first reached on a tie) and the others it spread to, then Pilots (`UniquePilots`, both sides, no NPCs), Ships (each pilot's distinct hulls, capsules included), and Kills (its killmails). All counts are from the search's killmails only.
- Its battle report links (zKillboard related, EVE Tools, Warbeacon: `api.ZkillRelatedURL`, `EveToolsRelatedURL`, `WarbeaconRelatedURL`) are for the main system at the hour of the battle's middle, in EVE time with minutes 00, ie `30005206/202610301200`. They sit in the row's last column as `siteLinks` icons (`SITE_LINKS` keys `evetoolsUrl`, `warbeaconUrl`, the favicons credited in ATTRIBUTION.md and About), and in its right-click menu above the system.
- Only battles with at least `battleMinPilots` (10) pilots, both sides together, are sent at all (user, 2026-10-30). It is paged like Killmails (`BATTLES_PER_PAGE` 20, `.paged-panel`), and At a glance's card notes how many battles were estimated.

## My Intel

- Everything from the bulk buttons up (help, warning, filter, add form, undo, bulk buttons) stays at the top of the window; only the cards (`.myintel-list`) scroll, as `.myintel-body` is a flex column that doesn't scroll itself.
- A warning under the window's help line (`.myintel-warning`) says affiliates can reach further back than the main: each list is paged on its own, so a busy main hits its page limit while a quiet affiliate goes on, and its oldest battles show only the affiliates' side. Raised 2026-10-29 from an MSF search whose 10 pages reached Oct 15th while its affiliates reached August; cutting the affiliates at the main's oldest killmail was offered and turned down for the warning.
- My Intel (app menu, `#myintel`, gui/myintel.go) shows and edits every holding and ignored ally: `GetMyIntel` builds a card (`IntelGroup`) per main and per target with ignored allies (`AllHoldingLinks`, `AllIgnoredAllies`, the targets' names, which ignored ally rows do not keep, looked up in bulk; corp and alliance tickers only from the cache, `CachedTicker`, blank until looked up, so the window opens at once).
- `LookupEntity`, `AddIgnoredAlly`, `RemoveIgnoredAlly`, `SaveHolding`, `RemoveHolding`, and `RemoveMyIntelGroup`/`RemoveMyIntelGroups` (a card's holdings and ignored allies, not links where it is another main's holding; the ticked cards' Delete, or a card's ×, after a confirmation, with an undo) change them without a search and skip `a.mu`; after a change the shown target's holdings and Allies are refreshed (`syncShownTarget`).
- Ticked cards (unticked by default; Check all ticks those the filter shows) export to a JSON file (gui/myintel_share.go, `intelFile`, format `gosleuth-intel` version 1: a `cards` list, each its entity, holdings with notes, and ignored allies, by type and id) for other users.
- An import is read at once, without the ESI, so it is fast and can not trip its rate limits: `planImport` skips malformed entries (counted once per entry), takes the file's names cleaned of control and formatting characters (`cleanImportedName`), and previews what it would add before `ApplyMyIntelImport`, which only adds, checked again against what is saved then, keeping the user's notes unless they take the file's.
- Every entity an import names is then saved to check (`retrieval.AddIntelChecks`, section `intel_check`, kept with the user's data) and `runIntelChecks` (gui/intel_checks.go) checks them in the background with no sign to the user: `universe/names` in batches of 1000 (`GetEntitiesFromEveIDs`, uncached), a batch the ESI 404s for one bad id split in half until it is found, correcting names to EVE's and removing holdings and ignored allies naming an entity that does not exist as the type the file said, with one ticker line only if it removed any. One runs at a time (`checkMu`); a failure keeps the checks; it runs after an import, at start, and first thing in `SearchTarget`, and shutdown stops it between calls (`closing`). Nothing claims a link is verified, as no check can prove one.

## Structures

- Structures (retrieval/structures.go, aggregate/structures.go, gui/structures.go) are pulled with the killmails in `CollectIntel`, before the report, and prefetched with them.
- Structure groups are sections of `structures.json`: `upwell_structure_groups` (citadels, engineering complexes, refineries), `control_tower_groups`, and control tower batteries `pos_battery_groups`, since a tower is never a killmail attacker, only its batteries. Structures with no guns, Metenox moon drills and customs offices, are `minor_structure_groups`: never a last structure lost, never on kills, but listed among previous losses and Destroyed. A killmail's structure is matched to these by its type's group in `fit_types.json` (`StaticValues.ContainsGroupOf`), which is why sdegen keeps control towers and the unpublished customs offices.
- A j-space system target gets `IntelReport.LastStructureLoss` and `PreviousStructureLosses` (`retrieval.StructureLosses`, page 1 of each structure and minor structure group's losses in the system, no limits: the newest non-minor loss, and the `PreviousStructureLosses` (5) newest others), the box above its Activity with the others collapsed under it.
- A corp or alliance target gets the Structures tab (`IntelReport.Structures`): Used in Kills is `CollectStructureKillmails`, each structure group's kills (not towers) and losses, and each battery group's kills, for the target and its holdings, to Max or Pages but ignoring the date limit, then `aggregate.StructuresUsed` groups them by type (towers as one kind), system, and owner corp, as killmails give no structure name or id, grayed by a loss of the same after its newest kill (which also names a tower seen only through batteries). A moon holds one tower, so towers are also told apart by their moon, zKill's nearest celestial on their kills (`StructureUse.MoonID`), and a tower loss counts only at its moon unless either moon is not known. A nearest celestial counts as a moon only when it is one of its system's moons (`aggregate.MoonOf`, checked against the cached system's planets by `systemMoons`), since it can be a planet, belt, or gate. A tower's moon is named on its rows and on a j-space system's structure losses (`moonName`, the ESI's universe/moons, cached as `types.MOON`); the ESI has no bulk call naming moons, so they are looked up 20 at a time before the rows are built (`PrefetchMoons`). Destroyed is `aggregate.StructuresDestroyed`, the structure and minor structure losses on the search's own killmails that the target's pilots were on. Lost (`StructuresReport.Lost`) is every upwell structure and control tower the target or a holding lost, from the same loss lists, newest first, whether or not it was ever on a kill (most towers never are), with its moon and the holding that lost it.

## Capital Pilots

- `GetCapitalPilots` (aggregate/capitalPilots.go) feeds a corp or alliance target's Capital Pilots tab: the target's non-NPC pilots on its killmails, victim or attacker, flying a capital, by ship type. A capital is a ship in `capital_groups` of `ships.json` (titans, dreadnoughts and lancers, carriers, supercarriers, force auxiliaries, capital industrials, freighters, jump freighters), matched by its type's group in `fit_types.json`, or one of `capital_types` (none built in, for edited copies).

## Fits

The full plan and the decisions behind it are in `.claude/docs/fits-plan.md`.

- **Building a fit.** `RawKillmail.Expand` builds each victim's `Fit` with `BuildFit` (retrieval/fits.go):
  - Each item's killmail flag is placed through `inventory_flags.json` (`comm.FitSlotOf`).
  - Each type is read from `fit_types.json` (`comm.FitTypeOf`). That file is generated from the SDE by `cmd/sdegen`, so type names cost no ESI call. Only victim types missing from it are prefetched from the ESI during the search, and they are listed in `Fit.MissingTypes`.
  - Charges pair with the module on the same flag.
  - Cargo keeps only `cargo_kept` types: charges, scripts, boosters and nanite paste.
  - Items nested under another item are dropped when the killmail is read.
- **Fits tab.** Pilot, corp and alliance searches get `IntelReport.Fits` (`buildFits`, gui/fits.go): the target's losses (holdings included) as `FitGroup`s, by ship name, then newest loss first.
  - Non-combat hulls are left out by category, group, or type (`ships.json` sections `fit_ignored_categories`, `fit_ignored_groups`, and `fit_ignored_types`: capsules, shuttles, corvettes, haulers and transports, freighters, mining and ORE ships, the Zephyr, yachts, structures, deployables, starbases), as is any loss with nothing fitted (`Fit.HasModules`).
  - Identical fits are one group (`fitKey`): the same hull with the same modules in each rack, in any order, each module counted as its base type (`comm.BaseType`, from `static_data/fit_variations.json`), so T1, T2, meta, faction, deadspace and officer variants of one module don't split a fit. The base type is the SDE's `variationParentTypeID` (sdegen, `ExtractVariations`). Mutated (abyssal) modules have none, so they are their own base type and a fit with one merges only with the same mutated modules (user's call 2026-10-30: unknown rolls would throw off the ranges). Different parents never merge, ie a Multispectrum Coating and a Multispectrum Energized Membrane, as that is a real fitting choice (user's call 2026-10-30). Charges, drones and cargo don't count, since they are easily used up or forgotten before the ship dies. A module in one of `fit_merged_groups` (`items.json`, built in: ECM) counts as its group, so a fit's ECM flavors, racial, Multispectral, or any tier, don't split it; each loss still shows its own. For a corp or alliance this merges across pilots.
  - **The summary** (`FitGroup.Summary`, `buildSummary` in gui/fit_summary.go, nil for a fit lost once) lays the losses side by side: each slot as its base type, each rack sorted by base name with empty slots last, each slot's `Variants` (the real modules its losses fitted, by how many losses, ties to the most common loss's); `CommonLoss`, the most common exact fit (real types, ECM still merged), ties to the earliest in `Losses`; `Pilots`; and `Stats`, each mode's lowest (`Min`) and highest (`Max`) of every number, each taken alone, so the two ends need not be one real loss. Drones and fighters are the common loss's. Implants are every one any loss had, once each in slot order, with how many losses had it as its quantity (`summaryImplants`), and `Implanted` counts the losses with any. No charges or boosters.
  - A capsule lost with implants is not a fit, but its implants go to the ship the pilot lost before it in the same battle, the latest if several (`podsWithShips`, with `aggregate.CollectedData.BattleOfKillmail`). A capsule can outlive its ship by a long while, even through a gate. zKill's API doesn't link the two. Implants and boosters are in slot order, from the extract's `head_slot`.
  - The loss carries `PodKillmailID` and `PodURL`, the zKillboard button's right-click menu opens the capsule, and Show fit on the capsule's killmail selects the ship. A fit with such a loss is marked `Implants`, listed first among its hull's fits, and tagged Implants, as is the loss when shown. Its losses with the most implants come first, so picking a merged fit opens on one of those. Implants don't decide which fits merge.
  - A group with a mutated module on any of its losses is marked `Abyssal`, from the `abyssal` flag `cmd/sdegen` sets on types in the Abyssal meta group, and tagged Abyssal.
  - The tags are rounded pills showing their names: Abyssal always red, Implants in the theme's `--badge` (its accent, or steel blue in the default theme, whose accent is the highlight's gold). The tag key explains them (`FIT_KEY`). Mutated drones don't count, as drones don't decide the fit.
  - **Rule tags** (Tackle, Neut, Logi, Cyno, ...) are read from each loss's modules, drones, hull, and the implants of its capsule by `static_data/fit_tag_rules.json` (`comm.LoadFitTagRules`, `retrieval.Fit.Tags`). How the rules work is in fits-plan.md phase 3, and how to edit them in docs/static-data-overrides.md. Each `FitLoss` has its own `Tags`, as drones, implants, and merged flavors (ie ECM) can differ between a fit's losses, so one loss with a capsule's implants can tip a tag onto the whole fit, and the `FitGroup` has every tag any of them has (`retrieval.MergeFitTags`, keeping each tag's copy furthest past its threshold, so the order of the losses can't change which names the fit), so its row shows why the filter matched it. Each loss's tags are read with `Fit.TagsWith`, whose `FitTagContext.NPCs` (`aggregate.PvENPCs`, the rats on its killmail) only `npcs` signals read: Ratting's nudge. They come in `priority` order, those without one last, and those sharing a priority by how far past their threshold each is (`passedBy`).
    - **Affiliate** (`affiliateTag`, gui/fits.go) is a hidden tag, shown like the weapon and range tags, on a loss whose victim flew for one of `IntelTarget.Holdings` and not the target itself (`affiliateOf`, by the victim's corp and alliance at the time, not `Killmail.Via`, as a killmail on both lists is kept as the main's). Its meaning names the affiliate.
    - **Fleet Doctrine** is read in `buildFits` from battles and the fit's other losses, not the fit (aggregate/fleetDoctrine.go, numbers under the tag's `fleet_doctrine`). `FleetDoctrineInBattle` gives it to a loss whose battle has `battle_hulls` pilots of its hull on its side (the victim included; the side is the target and its holdings plus the victim's alliance, or corp outside one, from every killmail of the battle) and `battle_logi` in `logi_groups`/`logi_types` hulls. `FleetDoctrineRepeated` gives it to every loss of a merged fit lost `repeat_losses` times by `repeat_pilots` pilots within one alliance (the target and holdings as one), its reasons appended after any from the loss's battle (`withDoctrineReasons`). Its reasons carry `Needed`, and the tip shows "7 of 5 needed" for them instead of a weight; a merged fit keeps the copy whose nearest reason passes its number furthest (`passedBy`), so the row shows its strongest battle. tagcheck never shows it, having no battle.
    - The first `role` names the row, before the date, with what gave it weight on hover. Beneath, the first 3 shown tags (`FIT_ROW_TAGS`), the naming one included so it is always where the tags are, are pills tinted in the theme's highlight (`fit-tag-rule`), then Abyssal and Implants. Every tag shows its full name. Hidden tags (the weapons, Close and Long) never show in the list or the key, nor name a row; they are filtered, and the fitting window shows them last, muted with a `--border` outline (`fit-tag-hidden`).
    - The fitting window lists every tag of the loss by name, hidden ones last and muted, under the loss's line (`fit-view-tags`). Hovering or focusing one shows `#fit-tag-tip` (`showFitTagTip`), one tip fixed to the page so the window's scrolling can't clip it, under the tag or over it when there is no room below, and hidden on any scroll: the tag's meaning, a row for each `FitTagReason` (module, drone, hull, or another tag through `tag_weights`, with its count and the weight it gave, negatives in red; the part a hull bonus added, `FitTagReason.Bonus`, is its own "↳ hull bonus" row beneath, so the rows add up), then the total against its threshold, and its rack share against `share_threshold` where it has one. Clicking one filters by it.
    - **The tag key** is not in the tab's help. The Tag key button beside the filter opens it on the left (`openFitKey`, `#fit-key-panel`), shrinking the sidebar to its icons without saving that choice, and the fit list to 180-220px (`#intel-tabs.fit-key-open`), so at the default window size the ring still fits without a sideways scroll (`main`'s max-width is 1320px for this); closing it, its ×, the sidebar's toggle, or leaving the tab gives the sidebar back as it was (`fitKeyCollapsedBefore`). It lists the shown rule tags this search found (`fitRuleTags`, `FIT_KEY`'s `items` getter), then Abyssal and Implants, refilled on a new search, each tag over its meaning with a line between entries. Clicking one (or Enter on it) filters by it like any other tag (`filterFitsByTag`, a key item's `onClick` in `helpContent`).
    - The filter finds a tag by its full name, or a start of 3 letters or more that fits only it (`fitTagNamed`, `FIT_TAG_PREFIX`), hidden ones too, so a short word such as part of a pilot's name stays a word. A fit has a tag if any of its losses does (`fitHasTag`).

## Static data overrides

- The user guide is `docs/static-data-overrides.md`; keep it in step with the files' sections and these rules.
- A json file in the `static_data` folder beside the exe (`staticdata.Overrides()`) is merged over the built-in file of the same name (`comm.loadMerged`, `mergeJSON`), so it need only hold what it adds or changes: objects merge key by key, an id or key set to `null` is removed, and anything else, lists included (`inventory_flags.json`'s slots, a j-space system's statics), is replaced whole. For example `{"capital_groups": {"513": null}}` as `ships.json` stops freighters counting as capitals, and `{"types": {"587": {"group": 26}}}` as `fit_types.json` changes only the Rifter's group.
- A copy that is not one json object (`mergeJSON` rejects `null`, lists, and trailing text), or whose merge its loader rejects (a section of a sectioned file removed, `fit_types.json` with no types, `jspace_statics.json` with no systems or a system given a code it does not list), is skipped with a warning and the built-in file is used. Debug mode's `session.json` lists the copies in the folder with their hashes, and the bundle holds each of them under `static_data/` (`overrideFiles`, `writeDebugBundle`).
- Preferences > Advanced > Game data > Export game data (`App.ExportStaticData`, gui/static_data.go) writes every file as loaded, merged and indented (`comm.StaticDataFiles`), to `static_data_export` beside the settings with a `README.txt` saying editing them changes nothing, then removing any other json a previous export left (`os.ReadDir`, as a glob would read brackets in the user's folder names), and opens the folder with the readme selected.

They are cached in the `image` section (retrieval/images.go), expiring only with a new SDE. A failed image is logged and drawn as a plain box.
